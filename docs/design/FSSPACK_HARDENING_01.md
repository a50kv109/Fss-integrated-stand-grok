**Итоговый статус hardening:** **`HARDENING PASSED WITHIN TESTED SCOPE`**

## 1. Подтверждение исходных рисков

В ходе предварительного аудита (FSSPACK AUDIT 02) в самописном PKZIP v2.0 распаковщике `tools/fsspack-prototype/zip_container.ts` были зафиксированы два потенциальных риска:
1. **Риск Path Traversal (управление именами записей):** Отсутствие строгой валидации путей записей при распаковке могло допустить проникновение абсолютных путей (`/etc/passwd`) или относительных директорий (`../`). Хотя текущая архитектура распаковывает данные в память (`Map<string, Buffer>`), а не на диск, некорректные или вредоносные имена записей создавали угрозу манипуляции внутренним индексом и логикой поиска обязательных файлов.
2. **Риск Zip Bomb / исчерпания ресурсов:** Отсутствие ограничений на размер архива, количество записей, размер распакованных файлов и суммарный объём распакованных данных могло привести к исчерпанию оперативной памяти (OOM) на приемной стороне (Стенд B) при обработке специально сформированных архивов.

**Результат проверки модели угроз:**  
Оба риска подтверждены как архитектурные уязвимости для ненадежных источников. Устранение выполнено в модуле `zip_container.ts`.

---

## 2. Причина и механизм каждого дефекта

- **Дефект 1 (Path Traversal & Malformed Paths):** Ранее метод `unpack()` считывал `filename` из заголовков архива и сохранял в `Map` без проверки символов. Злоумышленник мог сформировать записи с именами вроде `../../malicious`, `\windows\system32`, или дублирующиеся имена, вызывающие коллизии.
- **Дефект 2 (Zip Bomb & Resource Exhaustion):** Ранее декомпрессия через `zlib.inflateRawSync()` выполнялась без лимитов на размер выходящего буфера. Архив размером в несколько килобайт со сжатыми нулями мог распаковаться в оперативной памяти до гигабайт, обрушив процесс Node.js.

---

## 3. Принятые защитные меры

В класс `ZipContainer` (`tools/fsspack-prototype/zip_container.ts`) внедрены следующие защитные барьеры:
1. **Строгая санитизация путей (`sanitizeAndValidatePath`):**
   - Нормализация всех обратных слэшей (`\`) в прямые (`/`).
   - Безусловный отказ (`throw Error`) при обнаружении абсолютных путей (начинающихся с `/` или букв дисков вида `C:`).
   - Безусловный отказ при обнаружении сегментов `..` (directory traversal).
   - Отказ при наличии нулевых байтов (`\0`) или пустых сегментов.
   - Защита от коллизий: проверка на дублирующиеся имена в архиве (`files.has(filename)`).
2. **Лимиты ресурсов (Zip Bomb Defense):**
   - Ограничение максимального размера входящего ZIP-буфера (`MAX_ZIP_FILE_SIZE = 50 MB`).
   - Ограничение максимального количества записей в архиве (`MAX_ENTRIES = 200`).
   - Ограничение максимального размера распакованных данных для одного файла (`MAX_FILE_UNCOMPRESSED_SIZE = 10 MB`).
   - Ограничение суммарного объема распакованных данных по всему архиву (`MAX_TOTAL_UNCOMPRESSED_SIZE = 25 MB`).
   - Валидация методов сжатия: разрешены исключительно методы `0` (STORE) и `8` (DEFLATE). Любые иные методы (custom/bzip2/lzma) отклоняются.
   - Проверка совпадения фактической длины распакованного буфера с объявленным в заголовке `uncompressedSize`.
   - Проверка CRC-32 контрольной суммы.

## 4. Выбранные лимиты и обоснование

| Ограничение | Значение | Обоснование для кристаллографических пакетов (`.fsspack`) |
| :--- | :--- | :--- |
| **MAX_ZIP_FILE_SIZE** | 50 MB | Типичный размер `.fsspack` (с математикой и CIF) составляет от 2 КБ до 2 МБ. 50 МБ с запасом покрывает любые крупные экспериментальные наборы. |
| **MAX_ENTRIES** | 200 записей | Стандартный пакет содержит 4–10 файлов. 200 записей достаточно для сложных наборов спектров и структур без риска DoS по количеству дескрипторов. |
| **MAX_FILE_UNCOMPRESSED_SIZE** | 10 MB на файл | Ни один JSON модели или CIF-файл отдельной группы не превышает сотен килобайт. Лимит в 10 МБ на файл предотвращает раздувание памяти. |
| **MAX_TOTAL_UNCOMPRESSED_SIZE** | 25 MB суммарно | Полный архив со всеми вспомогательными материалами не должен превышать 25 МБ в распакованном виде. |

## 7. Оставшиеся риски и ограничения

1. **Изолированный контекст:** Защитные меры реализованы на уровне PKZIP-распаковщика в памяти. При будущей интеграции в веб-интерфейс (браузер) или сервер (`server.ts`) необходимо убедиться, что загрузка файлов через UI также проходит аналогичную предварительную проверку размера и типа перед передачей в `Gatekeeper`.
2. **Версионирование формата:** Введённые ограничения не меняют структуру полей `.fsspack` v1.0.0, поэтому обратная совместимость со всеми ранее созданными пакетами полностью сохранена.
