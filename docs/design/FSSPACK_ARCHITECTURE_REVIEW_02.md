## 1. Краткое резюме аудита исходного проекта

Проведён независимый статический и динамический аудит кодовой базы FSS V2. Исследовано состояние математических модулей, схем обмена данными, валидаторов, тестов и пользовательского интерфейса.

### Факты, подтверждённые кодом (`CODE_CONFIRMED`):
1. **Представление операций и точная арифметика:**
   - Вся кристаллографическая арифметика трансляций реализована в классе `ExactRational` (`core/schema/crystallographic_exchange.ts`). Дроби хранятся на базе `BigInt` (`bigN`, `bigD`), сокращаются через алгоритм Евклида (`bigGcd`), приводятся к периодическому интервалу $[0, 1)$ через `mod1()` и строго валидируются на границе преобразования в числа JavaScript через `Number.isSafeInteger`.
   - Операции симметрии представлены типом `ExchangeSymmetryOperation`: целочисленная матрица поворота/инверсии $W \in M_3(\mathbb{Z})$ (размером $3 \times 3$) и вектор рациональных трансляций $w \in \mathbb{Q}^3$ (`[Rational, Rational, Rational]`).
   - Использование чисел с плавающей запятой (`float`) в канонических операциях и ключах хеширования полностью исключено.

2. **Математическая модель групп и аксиоматика:**
   - Модуль `core/schema/crystallographic_exchange.ts` содержит функцию `validateMathematicalGroup`, проверяющую:
     - наличие тождественного элемента ($W = I_3, w \equiv 0 \pmod{\mathbb{Z}^3}$);
     - строгую двусторонность обратных элементов ($O_1 \circ O_2 \equiv I \land O_2 \circ O_1 \equiv I \pmod{\mathbb{Z}^3}$);
     - замкнутость относительно аффинной композиции $x' = W_1(W_2 x + w_2) + w_1 = (W_1 W_2)x + (W_1 w_2 + w_1) \pmod{\mathbb{Z}^3}$;
     - отсутствие скрытых дубликатов в множестве операций (равенство числа заявленных и уникальных канонических операций).
   - Модуль `core/group_closure.ts` (GCL-01) реализует детерминированное построение подгруппы из генераторов методом поиска в ширину (BFS) по модулю $\mathbb{Z}^3$ на `BigInt` с ресурсным ограничением `maxSize` (по умолчанию 192) и обязательной валидацией обратных элементов для всех полученных операций (`ISOLATED_MODULE_TESTED`, 15/15 PASS).

3. **Сдвиг начала координат и сравнение представлений:**
   - В `core/reference_loader.ts` реализован `OriginShiftAnalyzer`, вычисляющий точное преобразование операций при сдвиге начала координат $x' = x - x_0$ по формуле:
     $$w' = w + (W - I)x_0 \pmod{\mathbb{Z}^3}$$
     и доказывающий эквивалентность наборов операций при заданном рациональном векторе сдвига $x_0$ (проверено на SG 19 $P2_12_12_1$ со сдвигом $x_0 = (1/4, 1/4, 1/4)$).

4. **Аналитические свойства и иерархия доказательств:**
   - В `core/group_properties.ts` (`CrystallographicGroupProperties`) реализованы: расчет порядков матриц с ограничением $\{1, 2, 3, 4, 6\}$, нахождение точного центра инверсии $c = \frac{1}{2}w \pmod{\mathbb{Z}^3}$, итерация аффинных степеней $(W, w)^k$ с сохранением нередуцированных сумм трансляций $t_{\text{unreduced}} = \sum_{j=0}^{k-1} W^j w$ и выделением собственной трансляции $\tau = \frac{1}{k} t_{\text{unreduced}}$.
   - В `core/property_evidence.ts` зафиксирована 8-уровневая модель свидетельств (`SOURCE_VERIFIED`, `STRUCTURALLY_VALID`, `GROUP_AXIOMS_VERIFIED`, `PROPERTY_COMPUTED`, `PROPERTY_VERIFIED`, `REFERENCE_VERIFIED`, `INCOMPLETE`, `CONFLICT`).

5. **Автономные исследовательские модули:**
   - В `core/stl/` (Symmetry Transformation Lab V1) реализована точная проверка матричной сопряженности $g' = P^{-1} g P$ в $\mathbb{Q}^{n \times n}$ ($n \in \{2, 3\}$) на собственных классах `ExactScalar` и `ExactMatrix` (`INTEGRATED_STANDALONE_MODULE`, 7/7 PASS).
   - В `core/engine.ts` и `core/dimension.ts` реализован полигон 3D-геометрии (тетраэдр, инвариантные подпространства, сохранение связности ребер, тензор ковариации).

### Факты отсутствия в коде (`CONFIRMED_ABSENT`):
- Формат `.fsspack` отсутствует в коде (нет парсеров, упаковщиков, распаковщиков или схем).
- Нет понятий `PackageExporter`, `Gatekeeper` (как сетевого/файлового модуля приемки) и `WorkspaceStore` (как хранилища 3–5 активных / 10 локальных групп Стенда B).
- Нет протокола передачи «заявление источника $\neq$ факт для приемника» на уровне сериализованного файла.
- Нет связи между внешними физическими материалами (CIF, минералы, фазы) и математическим паспортом группы.

### Главный архитектурный вывод аудита:
Текущая кодовая база FSS V2 де-факто представляет собой **Стенд A (Reference / Processing)** с богатым математическим аппаратом и внутренним форматом обмена `SpaceGroupRecord`. Переносимый объект `.fsspack` должен стать **внешним отчуждаемым стандартом**, строящимся поверх проверенной модели обмена `core/schema/crystallographic_exchange.ts`, а не слепком памяти реестра `SymmetryCatalog` или состояния UI.

## 3. Предварительная логическая модель переносимого объекта (.fsspack)

Объект `.fsspack` проектируется как самодостаточный цифровой пакет, описывающий кристаллографическую группу в конкретной установке, со всеми математическими обязательствами, доказательствами проверок и внешними ссылками.

### Логические секции:

```text
.fsspack
├── A. Identity & Manifest      (Идентификация, соглашения, инвентарь пакета)
├── B. Mathematical Model       (Точные матрицы W, векторы w, правила решётки)
├── C. Verification Passport    (Паспорт проверок: свойства, методы, свидетельства, лимиты)
├── D. Research Profile         (Инварианты, подгруппы, гипотезы исследователя)
├── E. Related Resources        (Структуры, вещества, минералы, публикации - изолированно)
└── F. Provenance & Integrity   (Версии ядер, происхождение, контрольные суммы секций)
```

### Детальная спецификация секций:

#### Секция A. Identity & Manifest
- **Назначение:** Однозначная паспортизация объекта, системы координат, кристаллографических соглашений и состава пакета.
- **Обязательные поля:**
  - `fsspack_version` (string, semver, например `"1.0.0"`);
  - `package_id` (string, стабильный идентификатор объекта);
  - `space_group_number` (integer, [1, 230], если применимо);
  - `setting_id` (string, например `"P41"`, `"P21/c"`, `"P212121"`);
  - `symbols`: объект с международными обозначениями (`hermann_mauguin`, `hall`, опционально `schoenflies`);
  - `crystal_system` (enum: `triclinic`, `monoclinic`, `orthorhombic`, `tetragonal`, `trigonal`, `hexagonal`, `cubic`);
  - `conventions`: обязательный блок соглашений:
    - `basis_type`: по умолчанию `"standard_crystallographic_cell"`;
    - `origin_choice`: integer (`1` или `2`), если группа допускает выбор начала координат;
    - `cell_choice`: integer (`1`, `2`, `3` для моноgroups);
    - `unique_axis`: enum (`"a"`, `"b"`, `"c"`);
    - `coordinate_handedness`: `"right_handed"`.
- **Необязательные поля:** альтернативные символы, текстовые комментарии к установке.
- **Условия отсутствия:** Секция A обязательна целиком; ни одно из обязательных полей не может отсутствовать в валидном пакете.

#### Секция B. Mathematical Model
- **Назначение:** Полное, математически замкнутое и детерминированное описание операций группы в заданной установке.
- **Обязательные поля:**
  - `arithmetic_model`: `"ExactRational_BigInt"`;
  - `order`: integer (порядок фактор-группы по решётке трансляций);
  - `lattice_centering`: enum (`"P"`, `"A"`, `"B"`, `"C"`, `"I"`, `"F"`, `"R"`);
  - `lattice_translation_vectors`: массив базовых центрирующих трансляций (для $P$ — `[[0,1],[0,1],[0,1]]`);
  - `translation_equivalence`: `"modulo_Z3"` (фиксация эквивалентности $w \sim w' \iff w - w' \in \mathbb{Z}^3$);
  - `operations`: массив элементов `ExchangeSymmetryOperation`:
    - `index`: integer;
    - `W`: массив $3 \times 3$ целых чисел (`safe_integer`), $\det W \in \{1, -1\}$;
    - `w`: тройка точных рациональных чисел `[Rational, Rational, Rational]`, где `Rational = { numerator: integer, denominator: positive_integer }`;
    - `triplet`: символическая запись Jones-Faithful (например, `"-y,x,z+1/4"`).
- **Необязательные поля:**
  - `generators_indices`: массив индексов операций, образующих минимальный набор генераторов;
  - `multiplication_table`: таблица Кэли для фактор-группы (для ускорения вычислений в Стенде B).
- **Связи:** Операции секции B являются входными данными (`inputs`) для проверок секции C.

#### Секция C. Verification Passport
- **Назначение:** Фиксация результатов математических проверок, выполненных Стендом A (или предыдущими валидаторами).
- **Обязательные поля:**
  - `checks_ledger`: массив объектов свидетельств (структура `PropertyEvidence`):
    - `check_id`: string (уникальный ID в пакете, например `CHK-01-GROUP-CLOSURE`);
    - `target_property`: string (например, `GROUP_AXIOMS_CLOSURE`, `IDENTITY_ELEMENT`, `TWO_SIDED_INVERSES`, `INTRINSIC_TRANSLATION_SCREW`);
    - `algorithm`: `{ name: string, version: string }`;
    - `evidence_level`: enum (`"MATHEMATICALLY_PROVEN"`, `"COMPUTED_AND_VERIFIED"`, `"SELF_CONSISTENCY_CHECKED"`, `"EXTERNAL_REFERENCE_MATCH"`);
    - `status`: enum (`"PASS"`, `"FAIL"`, `"NOT_CHECKED"`, `"INCONCLUSIVE"`, `"PARTIAL"`);
    - `result_details`: объект с точными вычисленными значениями (например, координаты центра инверсии или вектор $\tau$);
    - `limits_and_disclaimers`: массив явных ограничений метода (например, «проверено при maxSize=192»).
- **Условия отсутствия:** Массив может быть пустым (`[]`) только в черновых лабораторных пакетах; в этом случае статус пакета маркируется как `UNVERIFIED_DRAFT`.

#### Секция D. Research Profile
- **Назначение:** Исследовательские инварианты, взаимосвязи и научные заметки.
- **Поля:**
  - `invariants`:
    - `algebraic_orders_histogram`: частоты порядков матриц;
    - `trace_histogram`: распределение следов;
    - `is_centrosymmetric`: boolean;
    - `is_chiral`: boolean;
    - `is_polar`: boolean;
  - `subgroups_and_supergroups`: известные ссылки на родительские/дочерние группы;
  - `hypotheses_and_observations`: массив элементов с **обязательной маркировкой эпистемического статуса**:
    - `tag`: enum (`"ESTABLISHED_FACT"`, `"OBSERVATION"`, `"THEORETICAL_HYPOTHESIS"`, `"OPEN_QUESTION"`);
    - `statement`: string;
    - `basis_or_reason`: string.
- **Условия отсутствия:** Секция D опциональна; её отсутствие не препятствует использованию группы в экспериментах.

#### Секция E. Related Resources
- **Назначение:** Привязка физических кристаллов, минералов, публикаций и внешних баз данных без засорения математического ядра.
- **Поля:**
  - `materials`: массив объектов:
    - `material_id`: string;
    - `chemical_name`: string;
    - `formula`: string;
    - `mineral_name`: string (опционально);
    - `database_links`: массив `{ database: "COD" | "ICSD" | "MaterialsProject", id: string, url: string }`;
    - `crystallographic_provenance`: `{ source_paper: string, measured_temperature: string, cell_parameters: object }`;
    - `association_status`: enum (`"CONFIRMED_CRYSTAL_STRUCTURE"`, `"LITERATURE_CITATION_ONLY"`, `"HYPOTHETICAL_PHASE"`);
    - `disclaimer`: обязательное напоминание: *«Физическое вещество является экспериментальным примером реализации; математическая модель группы не зависит от координат конкретных атомов»*.
  - `literature`: массив библиографических ссылок (DOI, авторы, год).
- **Условия отсутствия:** Опциональная секция. При экспорте чистой абстрактной группы секция пуста.

#### Секция F. Provenance and Compatibility
- **Назначение:** Техническая совместимость, версии инструментов и контрольные суммы.
- **Обязательные поля:**
  - `source_data`: `{ origin_name: string, commit_or_version: string, license: string, url: string }`;
  - `required_kernel_capabilities`: массив строк с требованиями к математическому ядру принимающего стенда:
    - `"ExactRational_BigInt"`: обязательна поддержка точной рациональной арифметики на BigInt;
    - `"AffineComposition_Mod1_Z3"`: композиция аффинных преобразований mod 1;
    - `"Dimension_3D"`: 3D векторно-аффинное ядро;
  - `checksums`:
    - `canonical_algorithm`: `"SHA-256"`;
    - `canonical_serialization`: `"RFC-8785-JSON-Canonicalization"`;
    - `math_model_sha256`: хэш канонического представления секции B;
    - `package_manifest_sha256`: хэш манифеста;
    - `container_payload_sha256`: хэш полного пакета.

## 4. Анализ пяти блокирующих вопросов (Blocking Decisions)

### Вопрос 1. Идентичность группы, установки и математического содержимого

#### Факты из кода (`CODE_CONFIRMED`):
- В `SpaceGroupRecord` (`core/schema/crystallographic_exchange.ts`) уже присутствуют поля `spaceGroupNumber`, `settingId`, `hmSymbol`, `hallSymbol`, `originChoice`, `cellChoice`, `uniqueAxis`.
- В `core/reference_loader.ts` доказано, что для одной и той же группы № 19 ($P2_12_12_1$) существуют две разные установки: стандартная установка Gemmi (ITA Vol. A) и историческая установка реестра `core/registry.ts`. Они имеют одинаковый номер (19), одинаковый HM-символ, но разные матрицы/трансляции и различаются сдвигом начала координат $x_0 = (1/4, 1/4, 1/4)$.
- В `canonicalOperationKey` операция идентифицируется строкой `${JSON(W)}|${w mod 1}`.

#### Варианты решения:
- **Вариант 1.1 (Монолитный ID):** Один составной строковый ключ вида `SG019:P212121:ORIGIN1:STD`.
  - *Плюсы:* Простота передачи одной строкой.
  - *Минусы:* Хрупок к изменениям параметров, смешивает физический смысл с именем строки.
- **Вариант 1.2 (Трехуровневая иерархическая модель идентичности — РЕКОМЕНДУЕТСЯ):**
  - **Уровень 1 (Group Identity / Топологический класс):** Международный номер группы `spaceGroupNumber` $\in [1, 230]$ + символ Лауэ / точечной группы. Определяет абстрактную группу и изоморфизм.
  - **Уровень 2 (Setting & Coordinate Convention / Кристаллографическая установка):** `settingId` + `hallSymbol` + блок `conventions` (базис, выбор начала координат, уникальная ось). Определяет геометрическое погружение группы в трехмерное кристаллографическое пространство.
  - **Уровень 3 (Mathematical Content Digest / Контентный инвариант):** Детерминированный криптографический дайджест `content_sha256` канонизированного множества операций секции B. Гарантирует битовую идентичность конкретного набора матриц и рациональных трансляций.

#### Последствия для совместимости и рекомендация для v1:
**Рекомендация: Принять Вариант 1.2.**  
Стенд B никогда не сравнивает группы только по номеру или только по хэшу:
- Две записи с одинаковым `spaceGroupNumber`, но разными `content_sha256` — это **не ошибка**, а разные установки (settings) или разный выбор начала координат одной группы.
- Две записи с одинаковыми `content_sha256` — математически тождественны в заданном представлении.
- Вопрос открыт для владельца: требуется ли для Уровня 3 формировать URN вида `urn:fss:group:76:setting:P41:sha256:abcd...`?

### Вопрос 2. Полный набор операций или генераторы

#### Факты из кода (`CODE_CONFIRMED`):
- `classifyOperationSet` в `core/operation_set_match.ts` осуществляет поэлементное сопоставление канонических ключей (`matchStrict`). Если на вход поданы только независимые генераторы (например, 2 генератора для 4-элементной группы), матчер выдает вердикт `OPERATION_MISMATCH` или `NO_CANDIDATES`, поскольку динамическое замыкание в быстром классификаторе отключено.
- Модуль `core/group_closure.ts` умеет вычислять замыкание из генераторов, но требует времени вычислений и ресурсного лимита `maxSize`.
- Полнота набора операций в FSS V2 определяется строго: это фактор-группа аффинных преобразований пространства по подгруппе целочисленных решёточных трансляций $\mathbb{Z}^3$. Все операции нормализованы так, что компоненты трансляций $w_i \in [0, 1) \cap \mathbb{Q}$.

#### Варианты решения:
- **Вариант 2.1 (Только минимальные генераторы):** Переносить 1–3 матрицы-генератора и полагаться на то, что принимающая сторона сама выполнит замыкание через GCL-01.
  - *Плюсы:* Компактность файла.
  - *Минусы:* Принимающий стенд обязан тратить ресурсы на BFS-вычисление; риск превышения `maxSize`; если генераторы заданы в нестандартной ячейке, замыкание может стать бесконечным или привести к арифметическому переполнению.
- **Вариант 2.2 (Полный набор канонических операций фактор-группы — РЕКОМЕНДУЕТСЯ ДЛЯ v1):** Переносить полный список всех операций общего положения смежного класса $G / \mathbb{Z}^3$, где $w \pmod{\mathbb{Z}^3}$.
  - *Плюсы:* Приемник сразу получает проверяемый, конечный и однозначный список; мгновенная проверка аксиом за $O(N^2)$; полная совместимость с текущим `matchStrict` и `SymmetryRecord`.
  - *Минусы:* Больший объем JSON (для кубических групп — до 48 или 192 операций). Для кристаллографии 192 операции — это менее 20 килобайт, что абсолютно незначительно.
- **Вариант 2.3 (Гибрид):** Полный канонический список операций как обязательный базис + явная разметка индексов генераторов `generator_indices: [...]` внутри того же списка.

#### Последствия для совместимости и рекомендация для v1:
**Рекомендация: Принять Вариант 2.3 (Полный список операций + опциональные индексы генераторов).**  
Для пространственных групп конечный список операций является полным тогда и только тогда, когда:
1. Он содержит тождественную операцию $(I_3, \vec{0})$.
2. Каждая операция $(W, w)$ имеет обратную $(W^{-1}, -W^{-1}w \bmod 1)$ в этом же списке.
3. Множество замкнуто относительно композиции по модулю решётки: $\forall O_i, O_j \in S: (O_i \circ O_j \bmod 1) \in S$.
4. Порядок множества $N$ строго равен порядку кристаллографического точечного класса, умноженному на кратность центрирования решётки (например, для $P4_1$: $|4| \times 1 = 4$; для $C2$: $|2| \times 2 = 4$).

### Вопрос 3. Базис и начало координат

#### Факты из кода (`CODE_CONFIRMED`):
- В FSS V2 принято соглашение о левом матричном действии на вектор-столбец:
  $$x' = W x + w$$
  Композиция двух операций: сначала применяется $(W_2, w_2)$, затем $(W_1, w_1)$:
  $$(W_1, w_1) \circ (W_2, w_2) = (W_1 W_2, \; W_1 w_2 + w_1 \pmod{\mathbb{Z}^3})$$
  Это строго зафиксировано в функции `compose` в `core/schema/crystallographic_exchange.ts` (строки 210–235) и в `AffineOperationAlgebra.composeAffineExact` в `core/group_properties.ts` (строки 137–146).
- Преобразование начала координат: при смещении начала координат на вектор $x_0$ точка $x$ в новой системе имеет координаты $x' = x - x_0$. В `OriginShiftAnalyzer.applyOriginShift` (`core/reference_loader.ts`, строка 125) используется формула:
  $$w' = w + (W - I) x_0 \pmod{\mathbb{Z}^3}$$
- Преобразование базиса решётки $P \in GL_3(\mathbb{Z})$: в STL V1 (`core/stl/conjugacy.ts`) сопряжение матриц вычисляется как:
  $$g' = P^{-1} g P$$
  где $P$ — матрица перехода к новому базису.

#### Варианты решения:
- **Вариант 3.1 (Неявные соглашения):** Указывать только символы установки (например, `"P 21/c"`), надеясь, что второй стенд знает соглашения ITA по умолчанию.
  - *Плюсы:* Минимум полей.
  - *Минусы:* Катастрофический риск ошибок при несовпадении версий таблиц (например, monoclinic unique axis $b$ vs unique axis $c$; origin choice 1 на инверсии vs origin choice 2 на оси симметрии).
- **Вариант 3.2 (Явный декларативный блок координатных соглашений — РЕКОМЕНДУЕТСЯ):**
  Пакет обязан недвусмысленно фиксировать:
  1. `basis_vectors`: символическое или матричное описание базиса ячейки относительно стандартного кристаллографического репера.
  2. `origin_description`: текстовое описание положения начала координат (например, `"Inversion center at 0,0,0"` или `"Intersection of 2-fold axes"`).
  3. `shift_from_ita_standard`: явный рациональный вектор $x_0 \in \mathbb{Q}^3$, если установка сдвинута относительно первого стандартного выбора ITA Volume A.

#### Открытые вопросы владельцу:
- Считать ли выбор Origin Choice 1 по умолчанию обязательным для всех центросимметричных групп?
- Требуется ли в v1 поддержка произвольных непрерывных сдвигов начала координат или мы ограничиваемся дискретными кристаллографическими сдвигами (кратно 1/2, 1/4, 1/3, 1/6)?

### Вопрос 4. Политика импорта (Gatekeeper Acceptance Policy)

#### Факты из кода (`CODE_CONFIRMED`):
- В коде уже реализованы независимые слои валидации (`validateStructuralRecord`, `validateMathematicalGroup`, `validateProvenance`). Они возвращают раздельные отчеты об ошибках.
- Успешная валидация структуры гарантирует только отсутствие NaN и корректность типов; она не гарантирует замкнутость группы.
- Успешная математическая валидация подтверждает замкнутость конкретных матриц, но не доказывает, что эти матрицы соответствуют заявленному номеру группы в ITA.

#### Варианты решения:
- **Вариант 4.1 (Слепое доверие):** Стенд B проверяет только хэш SHA-256 файла; если хэш сошёлся, статус всех свойств из секции C считается доказанным.
  - *Плюсы:* Быстродействие.
  - *Минусы:* Полное крушение эпистемической дисциплины проекта. Стенд A может иметь ошибку в алгоритме, файл может быть подписан непроверенным источником.
- **Вариант 4.2 (Раздельная 5-ступенчатая политика Gatekeeper — РЕКОМЕНДУЕТСЯ):**
  Процесс импорта делит проверку на 5 независимых этапов с присвоением раздельных статусов:

```text
Входной файл .fsspack
   │
   ├─► 1. Integrity Check (Контрольные суммы частей и манифеста) ──► [INTEGRITY_OK / INTEGRITY_FAIL]
   │
   ├─► 2. Format & Schema Check (Синтаксис, ExactRational, safe_int) ──► [SCHEMA_VALID / SCHEMA_INVALID]
   │
   ├─► 3. Capability Compatibility (Поддержка версией ядра Стенда B) ──► [COMPATIBLE / INCOMPATIBLE]
   │
   ├─► 4. Mandatory Math Re-check (Локальная проверка аксиом группы ядром B) ──► [AXIOMS_VERIFIED / AXIOMS_REJECTED]
   │
   └─► 5. Provenance & Claims Evaluation (Оценка авторских утверждений) ──► [CLAIMS_ACCEPTED / CLAIMS_UNVERIFIED]
```

#### Статусная модель для импортированного экземпляра:
Приемник формирует собственный статус рабочей группы `WorkingInstance`:
- `VERIFIED_ACTIVE`: целостность подтверждена, аксиомы проверены локально, группа загружена в эксперимент.
- `PARTIALLY_CHECKED`: структура и базовые аксиомы сошлись, но сложные свойства (например, специфический инвариант или сдвиг начала координат) локально не перепроверялись и помечены как `PRODUCER_CLAIM_ONLY`.
- `REJECTED`: обнаружено несоответствие хэша, разрыв замкнутости или отсутствие обратного элемента.
- `INCONCLUSIVE`: алгоритм локальной проверки упёрся в ресурсный лимит (например, по `maxSize`).

### Вопрос 5. Хэширование и канонизация

#### Факты из кода (`CODE_CONFIRMED`):
- В `core/reference_loader.ts` функция `computeCanonicalSha256` рекурсивно сортирует ключи JavaScript-объектов по алфавиту перед сериализацией в JSON:
  ```typescript
  const sorted: Record<string, any> = {};
  Object.keys(obj).sort().forEach(k => { sorted[k] = canonicalize(obj[k]); });
  ```
  Это обеспечивает независимость от порядка ключей в объекте.
- **Критический пробел в существующем коде:** массив `records.operations` является упорядоченным списком. Если в двух файлах одни и те же операции записаны в разном порядке (например, в одном сначала $C_2$, потом инверсия, а в другом наоборот), функция `computeCanonicalSha256` выдаст **совершенно разные хэши**!
- То же самое касается представления рациональных чисел: дробь $2/4$ и дробь $1/2$ в наивном JSON дадут разные строки, если они предварительно не сокращены через `ExactRational`.

#### Варианты решения:
- **Вариант 5.1 (Только побайтовый хэш файла):** Хэшировать итоговый ZIP-архив `.fsspack`.
  - *Плюсы:* Легко проверить утилитой `sha256sum`.
  - *Минусы:* Недетерминированность упаковщиков ZIP. Разные версии архиваторов (или разные даты создания файлов внутри ZIP) дают разные хэши для абсолютно идентичного математического содержания.
- **Вариант 5.2 (Двухуровневое раздельное хэширование — РЕКОМЕНДУЕТСЯ):**
  1. **Container Byte Hash (`file_sha256`):** Контрольная сумма физического файла (для контроля передачи по сети, скачивания и предотвращения повреждения диска).
  2. **Canonical Mathematical Digest (`content_sha256`):** Вычисляется по строгому математическому канону:
     - Все рациональные числа сокращаются до несократимого вида с положительным знаменателем ($d > 0, \gcd(|n|, d) = 1$) и нормализуются по модулю $\mathbb{Z}^3$.
     - Для каждой операции строится строгий строковый ключ `canonicalOperationKey`: `${JSON(W)}|${w_canonical}`.
     - Массив операций **сортируется лексикографически** по этим каноническим ключам перед хэшированием.
     - Сериализация выполняется строго по стандарту RFC-8785 (JSON Canonicalization Scheme).

#### Последствия для совместимости и рекомендация для v1:
**Рекомендация: Принять Вариант 5.2.**  
Не объявлять группы математически различными, если у них не совпал `file_sha256`. Различие математического содержания фиксируется только тогда, когда различаются их `content_sha256`.

## 5. Сравнение физических форматов контейнера

| Критерий сравнения | Вариант 1: ZIP-контейнер `.fsspack` (мультифайл) | Вариант 2: Единый канонический файл `.fsspack.json` | Вариант 3: JSON-манифест + sidecar-каталог ресурсов |
| :--- | :--- | :--- | :--- |
| **Переносимость** | **Высокая:** Один физический файл; передается через почту, API, флешку, GitHub Releases. | **Максимальная:** Один текстовый файл. Идеально для git-diff и текстовых редакторов. | **Низкая:** Папка с файлами легко теряет части при копировании и в веб-загрузках. |
| **Поддержка бинарных ресурсов** | **Отличная:** Нативные CIF-файлы, PNG-схемы, PDF-статьи хранятся в папке `resources/` без перекодирования. | **Плохая:** Требуется кодирование в Base64, что раздувает размер на 33% и усложняет парсинг. | **Хорошая:** Файлы лежат рядом на диске. |
| **Выборочное чтение (Streaming / Partial Read)** | **Отличная:** Можно прочитать только `manifest.json`, не распаковывая тяжелые приложения. | **Средняя:** Необходимо распарсить весь JSON-документ целиком в память. | **Отличная:** Читается только нужный файл с диска. |
| **Контроль целостности** | **Модульный:** Хэши каждого внутреннего файла фиксируются в манифесте; повреждение картинки не ломает математику. | **Монолитный:** Любое изменение пробела в комментарии меняет общий хэш файла. | **Сложный:** Требуется отдельный файл сумм (типа `sha256sum.txt`). |
| **Детерминизм хэширования** | **Требует нормализации:** ZIP хранит timestamps и права доступа; требуется упаковка с нулевыми датами (как в APK/JAR). | **Детерминирован:** Прямое применение алгоритма канонизации RFC-8785. | **Не детерминирован** как единый объект. |

### Предварительная рекомендация для FSS V2:
1. **Для чистых математических объектов (без тяжелых изображений):** Допускается компактный формат `SG076_P41.fsspack.json` (Вариант 2), полностью валидируемый стандартными JSON-схемами.
2. **Для полных исследовательских пакетов (с CIF-структурами и статьями):** Стандартный контейнер ZIP с расширением `.fsspack` (Вариант 1), внутри которого лежат канонические JSON-секции и каталог `resources/`.

### L.1. Сводка предварительных архитектурных решений

1. **Решение по контейнеру:**
   - Нормативным форматом пакета является ZIP-архив с расширением `.fsspack`. Внутри архива располагаются структурированные JSON-документы (манифест, модель, верификация, происхождение) и опциональный каталог дополнительных материалов `resources/`.
   - Введение альтернативного текстового формата `.fsspack.json` признано нецелесообразным, так как дублирование нормативных форматов усложняет валидацию и фрагментирует экосистему.
2. **Решение по политике приёма:**
   - Процесс импорта и допуск к эксперименту строго разделены во времени и логике. Недопустимый или повреждённый пакет безусловно отклоняется. Пакет с непроверенными или неполными свойствами может быть принят в карантинный/диагностический режим, но полноценная активация в экспериментальной среде требует выполнения обязательных локальных математических проверок.
3. **Решение по именованию и идентичности:**
   - Имя файла на диске (например, `SG076_P41.fsspack`) служит лишь пользовательским ярлыком и не является источником математической идентичности. Устойчивые идентификаторы группы, установки и соглашений хранятся исключительно внутри структуры пакета. Хэш математического содержимого вычисляется независимо.
4. **Решение по пилотному объекту:**
   - Пространственная группа № 76 ($P4_1$) утверждена в качестве предварительного кандидата для первого сквозного испытания переноса между Стендом A и Стендом B.

### L.2. Уточнение A: Минимальная структура ZIP-контейнера (.fsspack)

Пакет `.fsspack` представляет собой стандартный ZIP-архив со следующей канонической раскладкой файлов:

```text
SG076_P41.fsspack (ZIP Archive)
├── manifest.json              # [ОБЯЗАТЕЛЬНО] Паспорт пакета, версии схем, инвентарь и хэши
├── math-model.json             # [ОБЯЗАТЕЛЬНО] Точные матрицы W, векторы w, решётка, центрирование
├── verification.json           # [ОБЯЗАТЕЛЬНО] Свидетельства математических проверок (checks ledger)
├── provenance.json             # [ОБЯЗАТЕЛЬНО] Источник данных, коммит, лицензия, инструмент сборки
├── research-profile.json       # [ОПЦИОНАЛЬНО] Инварианты, спектры порядков/следов, гипотезы
└── resources/                  # [ОПЦИОНАЛЬНО] Связанные внешние материалы
    ├── structure.cif           # Экспериментальные кристаллические структуры (при наличии)
    └── literature.json         # Ссылки на первоисточники и научные публикации
```

#### Назначение каждого файла:
1. `manifest.json`: Точка входа для Gatekeeper'а. Содержит `package_id`, `fsspack_version`, `space_group_number`, `setting_id`, карту соглашений `conventions`, список всех файлов архива с их относительными путями и пофайловыми контрольными суммами SHA-256. Позволяет проверить целостность пакета без распаковки всех вложений.
2. `math-model.json`: Ядро описания группы. Содержит порядок группы, тип центрирования решётки, векторы центрирования, соглашение об эквивалентности по модулю $\mathbb{Z}^3$, а также полный массив операций в каноническом представлении `ExchangeSymmetryOperation` с точными рациональными числами `ExactRational`.
3. `verification.json`: Паспорт доказательств. Содержит массив `checks_ledger`, документирующий, какие свойства проверялись Стендом A, какими алгоритмами, с какими входными данными и результатами. Для каждого пункта фиксируется статус (`PASS`, `FAIL`, `NOT_CHECKED`, `INCONCLUSIVE`, `PARTIAL`).
4. `provenance.json`: Метаданные происхождения. Хранит сведения об исходной базе (Gemmi, ITA, CCTBX), хэш коммита upstream-репозитория, лицензионные ограничения (например, MPL-2.0) и требования к математическому ядру (`required_kernel_capabilities`).
5. `research-profile.json`: Дополнительный исследовательский профиль (инвариантные спектры, подгруппы, энантиоморфизм, полярность) с обязательным тегированием гипотез исследователя (`ESTABLISHED_FACT` vs `THEORETICAL_HYPOTHESIS`).
6. `resources/*`: Изолированное хранилище тяжелых или эмпирических данных (файлы CIF, спектры, описания минералов). Данные файлы изолированы от математического ядра: повреждение CIF-файла не делает недействительной кристаллографическую группу.

### L.3. Уточнение B: Политика приёма (Gatekeeper) и статусные состояния

Входной контроль Стенда B строится на принципе нулевого безусловного доверия («Producer claim $\neq$ Receiver truth»). Процесс разделен на 5 последовательных стадий:

```text
                 Входной пакет .fsspack
                           │
  [Стадия 1]               ▼
  Структурный приём: Чтение ZIP, наличие manifest.json, синтаксис JSON
     ├─► ОШИБКА ──► Статус: REJECTED (Сообщение: Нечитаемый ZIP / Повреждённый JSON)
     └─► УСПЕХ ───┐
                  ▼
  [Стадия 2]      
  Проверка целостности: Сверка SHA-256 каждого файла с manifest.json
     ├─► ОШИБКА ──► Статус: REJECTED (Сообщение: Несоответствие контрольной суммы)
     └─► УСПЕХ ───┐
                  ▼
  [Стадия 3]      
  Проверка совместимости: Поддержка версий схем и возможностей ядра (BigInt, Mod1)
     ├─► ОШИБКА ──► Статус: REJECTED (Сообщение: Неподдерживаемая версия ядра Стенда B)
     └─► УСПЕХ ───┐
                  ▼
  [Стадия 4]      
  Математическая перепроверка: Локальный запуск validateMathematicalGroup ядром B
     ├─► ОШИБКА ──► Статус: REJECTED (Сообщение: Нарушение аксиом группы в модели)
     └─► УСПЕХ ───┐
                  ▼
  [Стадия 5]      
  Решение о допуске: Анализ полноты проверок в verification.json
     ├─► Все проверки PASS ──────────► Статус: VERIFIED_ACTIVE (Допуск к экспериментам)
     └─► Есть NOT_CHECKED/PARTIAL ───► Статус: QUARANTINE_DIAGNOSTIC (Карантинное хранение)
```

#### Статусные состояния объекта в Стенде B:
- `REJECTED`: Пакет отклонён на ранних стадиях (1–4). Файл не сохраняется в локальной библиотеке. Пользователю выводится детализированный отчёт о причинах отказа (с указанием конкретного файла, поля или нарушенной аксиомы).
- `QUARANTINE_DIAGNOSTIC`: Пакет целостен, синтаксически корректен и локально замкнут, однако в секции `verification.json` часть важных свойств имеет статус `NOT_CHECKED`, `INCONCLUSIVE` или `PARTIAL`. Пакет помещается в локальное хранилище (`WorkspaceStore`) с жёлтым индикатором «Карантин». Группа доступна для инспекции паспорта и локального запуска недостающих проверок, но **заблокирована для участия в сравнительных полиэдрических экспериментах и матричном сопряжении** до прохождения всех тестов.
- `VERIFIED_ACTIVE`: Пакет полностью проверен (локально пересчитаны тождество, обратные, замкнутость и специфические инварианты). Группа получает зелёный индикатор и может быть активирована в рабочий слот экспериментатора (в лимит 3–5 активных групп).

### L.4. Уточнение C: Идентичность и каноническое хэширование

Проведён детальный статический анализ функций `computeCanonicalSha256` (`core/reference_loader.ts`) и `canonicalOperationKey` (`core/schema/crystallographic_exchange.ts`).

#### Факты из кода (`CODE_CONFIRMED`):
1. **Что входит в текущий `computeCanonicalSha256`:**
   Функция принимает массив `SpaceGroupRecord[]`, рекурсивно сортирует ключи объектов (`Object.keys(obj).sort()`) и сериализует результат в компактный JSON без пробелов. В хэш попадают все поля записи, включая метаданные `provenance` (название источника, коммит, дата).
2. **Влияние порядка массива операций (`ARRAY_ORDER_SENSITIVITY`):**
   В коде `computeCanonicalSha256`:
   ```typescript
   if (Array.isArray(obj)) return obj.map(canonicalize);
   ```
   Сортировка массивов **не производится**. Если один и тот же набор операций записан в разном порядке (например, $O_1, O_2$ вместо $O_2, O_1$), функция выдаст **два абсолютно разных хэша SHA-256**!
3. **Учёт установки и соглашений:**
   Поля `originChoice`, `cellChoice`, `uniqueAxis` в текущем типе `SpaceGroupRecord` являются опциональными (`?`). Если они не определены (`undefined`), они просто опускаются из JSON, что делает невозможным различение установок, если они не зафиксированы в `settingId` или `hallSymbol`.
4. **Роль `canonicalOperationKey`:**
   В `core/schema/crystallographic_exchange.ts` функция `canonicalOperationKey` формирует строковый ключ: `${JSON(W)}|${w_canonical}`, где каждая координата трансляции нормализуется через `ExactRational(n, d).mod1().toString()`. Это гарантирует, что дроби $1/2$ и $2/4$, а также $3/2$ и $1/2$ дают идентичные канонические ключи.

#### Архитектурные требования для канонического хэша математического содержания (`content_sha256`):
Чтобы хэш математического содержимого определял именно математическую эквивалентность, а не случайности форматирования, необходимо реализовать следующий канонический алгоритм:
1. **Изоляция от метаданных источника:** Хэш вычисляется строго от секции B (`math-model.json`), исключая имена авторов, даты сборки и комментарии.
2. **Канонизация рациональных трансляций:** Каждая компонента трансляции нормализуется: знаменатель строго положителен ($d > 0$), числитель и знаменатель взаимно просты ($\gcd(|n|, d) = 1$), значение приведено к интервалу $[0, 1)$ по модулю целочисленной решётки.
3. **Лексикографическая сортировка операций:** Перед хэшированием массив операций **сортируется по алфавиту** по их ключам `canonicalOperationKey`. Это полностью устраняет зависимость от порядка следования операций в массиве.
4. **Каноническая сериализация по RFC-8785 (JCS):** Сериализация нормализованного объекта выполняется по стандарту RFC-8785 (лексикографический порядок ключей объектов, отсутствие незначащих пробелов, строгий формат чисел).

**Разделение хэшей:**
- `file_sha256`: Контрольная сумма физического ZIP-архива `.fsspack` (проверка передачи байтов по сети).
- `content_sha256`: Хэш канонизированного математического ядра (проверка математической тождественности моделей).

### L.5. Уточнение D: Исследование пилотной группы № 76 ($P4_1$)

Проведён анализ фактического представления Space Group No. 76 ($P4_1$) в кодовой базе FSS V2.

#### Факты из кода (`CODE_CONFIRMED`):
1. **Реальное представление в `core/registry.ts`:**
   Группа зарегистрирована под `groupNumber: 76`, `settingId: "P41"`, `hmSymbol: "P 41"`, `hallSymbol: "P 4w"`.
   Содержит ровно 4 операции общего положения:
   - $O_0$: $W = I_3$, $w = (0/1, 0/1, 0/1)$ — тождественный элемент $(x, y, z)$.
   - $O_1$: $W = \begin{pmatrix} 0 & -1 & 0 \\ 1 & 0 & 0 \\ 0 & 0 & 1 \end{pmatrix}$, $w = (0/1, 0/1, 1/4)$ — винтовой поворот $4_1$ вдоль оси $z$: $(-y, x, z + 1/4)$.
   - $O_2$: $W = \begin{pmatrix} -1 & 0 & 0 \\ 0 & -1 & 0 \\ 0 & 0 & 1 \end{pmatrix}$, $w = (0/1, 0/1, 1/2)$ — поворот 2-го порядка $2_1 = 4_1^2$ вдоль оси $z$: $(-x, -y, z + 1/2)$.
   - $O_3$: $W = \begin{pmatrix} 0 & 1 & 0 \\ -1 & 0 & 0 \\ 0 & 0 & 1 \end{pmatrix}$, $w = (0/1, 0/1, 3/4)$ — поворот $4_1^3$ вдоль оси $z$: $(y, -x, z + 3/4)$.
2. **Алгебраические характеристики:**
   - Все 4 матрицы имеют $\det W = +1$ (собственные вращения, chiral group).
   - Инверсия $W = -I_3$ и зеркальные плоскости отсутствуют.
   - Порядок матриц: $O_0$ — 1; $O_2$ — 2; $O_1, O_3$ — 4.
   - Винтовая ось $4_1$: четырёхкратное применение операции $O_1$ даёт чистую трансляцию вдоль оси $z$ на 1 элементарную ячейку:
     $$(W_1, w_1)^4 = (I_3, \; (0, 0, 1)) \equiv (I_3, \vec{0}) \pmod{\mathbb{Z}^3}$$
3. **Существующие тесты в кодовой базе:**
   - В `core/registry.test.ts` (строки 14, 76–112) для $P4_1$ выполняются: проверка наличия 4 операций, уникальность операций, наличие $I_3$, замкнутость относительно композиции по модулю $\mathbb{Z}^3$, наличие обратного элемента для каждой операции.
   - Скрипт `scripts/audit_sg76.ts` подтверждает самосогласованность группы.
4. **Изоляция от классификатора:**
   - В `core/operation_set_match.ts` массив `REGISTERED_SETTING_IDS` содержит ровно 8 настроек (Nos. 1, 2, 3, 4, 5, 9, 14, 19). Группа $P4_1$ исключена из массива. При вызове `classifyOperationSet` на операциях $P4_1$ возвращается вердикт `NO_CANDIDATES`.

#### Проверки, обязательные для выполнения Gatekeeper'ом Стенда B при приёме $P4_1$:
1. Проверка определителей: $\forall i: \det W_i = +1$ (подтверждение хиральности).
2. Проверка тождества: $O_0 = (I_3, \vec{0})$.
3. Проверка цикличности: проверка того, что $O_1$ порождает всю группу ($\operatorname{ord}(O_1) = 4$, $O_1^2 \equiv O_2$, $O_1^3 \equiv O_3$, $O_1^4 \equiv I \pmod{\mathbb{Z}^3}$).
4. Проверка собственной трансляции: итерация по KB-14 подтверждает, что нередуцированная сумма трансляций за 4 шага равна ровно $(0, 0, 1)$, что даёт собственный винтовой сдвиг $\tau = (0, 0, 1/4)$ вдоль кристаллографической оси $c$.

#### Сведения, необходимые для однозначного восстановления $P4_1$ без доступа к исходному коду:
- Кристаллографическая система: тетрагональная (`tetragonal`).
- Решётка: примитивная Браве (`P`), центрирующие трансляции отсутствуют.
- Ось винтового поворота: параллельна базисному вектору $c$ ($[0, 0, 1]$).
- Соглашение о начале координат: стандартное ITA Volume A (начало координат лежит на винтовой оси $4_1$).
